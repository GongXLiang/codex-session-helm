# 多项目上下文、回报队列与自动看板

适用于同一宿主上 2–3 个互不相关项目。Python 3.10+ 标准库即可运行；不安装服务、不需要 API key。简单任务继续使用经典任务卡或 `helm.py`。真实运行文件必须在项目或明确指定的运行目录，不能放进 Skill 仓库。

## 三个角色与唯一账本

| 角色 | 负责什么 | 不代替什么 |
| --- | --- | --- |
| 主管对话 | 冻结任务卡、原生派发、观察运行、领取审查、独立核验、修订与续接 | 不把执行者自检当成验收 |
| 执行对话 | 只处理一张任务卡，在所属项目写产物、报告和 outbox 事件 | 不直接改共享账本或其他项目 |
| 本地运行工具 | 持久化状态、去重、版本和写入冲突检查、排队、只读实时看板 | 不调用模型、原生桌面工具或自行推进任务 |

SQLite 是进度、队列、派发意图和裁决的权威入口。计划保存业务目标、定义与决策条件，报告保存详细证据，任务卡保存派发时的 Context。Markdown/JSON 看板与 `export` 都是派生结果，不能反向当成第二套可编辑状态。

身份使用 `project/workflow/task/revision/attempt` 加真实 `thread/host`。不同项目可以都有 `T01`；来源或版本不符的回报不会改变当前任务。项目隔离是文件路由和提示词范围约束，并非操作系统访问控制。不要给执行者全局数据库路径或其他项目正文；同一操作系统账号仍可能访问这些文件。

## 主管启动

1. 发现当前宿主的 `create_thread`、`send_message_to_thread`、`wait_threads`、分组及 `open_in_codex` 能力，复用已有授权。未获创建会话和双向通知授权时，沿用文档任务卡，不把启用运行工具当成授权。
2. 明确一个本地运行目录、主管真实 threadId、宿主和项目根目录。默认全局执行上限 3、待审查上限 4、一次最终审查；可按本轮约定降低。上限控制新派发，不拒收已经运行任务的回报。
3. 按 [项目配置示例](../examples/portfolio-project.json) 填写项目配置，所有任务初始为 planned/unknown。必须指定本项目实际根目录、plan、workflow 和具体 write_paths。计划、输入和任务卡先落盘；不要把已有 accepted 状态未经复核导入。

PowerShell 示例，值由现场实际路径替换：

```powershell
$helmScript = 'C:\path\to\session-helm\scripts\helm_runtime.py'
$helmDb = 'D:\work\coordination\.session-helm\ledger.sqlite'
$helmOwner = 'actual-supervisor-thread-id'
python $helmScript --db $helmDb --owner $helmOwner init
python $helmScript --db $helmDb --owner $helmOwner --epoch 1 register 'D:\work\project-a\project.json'
python $helmScript --db $helmDb snapshot
```

`init` 不覆盖已有账本，新账本启用 schema 3 上下文门禁。登记项目后按[主管上下文](主管上下文.md)保存带来源摘要。恢复时先读 portfolio，不重新初始化；epoch 以当前账本为准。旧 schema 1/2 账本须显式备份升级才具备新增门禁。

## 派发与上下文隔离

主管全局只保留每个项目的目标、阶段、阻塞、待审查数量和下一决定。先 portfolio，再 focus 当前项目；切换前 checkpoint。具体审查只读取该项目的任务卡、前置验收及本次报告。这个文件路由和版本门禁不删除模型聊天历史。

```powershell
python $helmScript --db $helmDb --owner $helmOwner --epoch 1 focus --project data
python $helmScript --db $helmDb context --project data --workflow main --task T01 --output 'D:\work\project-a\context-T01-v1.json'
python $helmScript --db $helmDb --owner $helmOwner --epoch 1 prepare --project data --workflow main --task T01
# 获得 action_id 后，通过原生 create_thread / send_message_to_thread 派发。
python $helmScript --db $helmDb --owner $helmOwner --epoch 1 bind --action 'actual-action-id' --thread 'actual-executor-thread-id' --receipt 'native-tool-receipt-path-or-reference' --output 'D:\work\project-a\binding-T01-v1.json'
```

`prepare` 在事务中预留并发和写入范围；依赖未验收、版本失效、队列积压、前一执行尚未核实 idle 或目录冲突时拒绝派发。`bind` 只记录原生工具实际回执，不证明执行已经开始。原生工具与 SQLite 无法做一个跨系统事务，因此不承诺 exactly-once 派发。

首条任务消息给出卡片和绑定文件路径，说明绑定可能稍后写入；执行者提交事件前必须读到真实绑定，缺失时回报缺口，不能猜 ID。创建后保存回执再 bind；后续任务优先沿用已有执行对话并提交新的 attempt。命令、native 回执和任务卡分别有据可查。

若派发工具超时，先用 `list_threads` / `read_thread` 对账：找到真实会话则 bind；只有确证没有发送时才 `cancel-dispatch --action ID --evidence REF` 后重新 prepare。超时本身不是未发送证据。该命令不会停止任何会话或进程。

任务卡中的模型决策仍按[模型与思考强度](模型与思考强度.md)执行；运行工具不决定或切换模型。

## 执行者发布回报

执行者只需读当前任务卡、绑定文件和本节。输入/输出边界以任务卡为准。完整回报和产物先落盘并读回，再执行：

```powershell
python $helmScript publish --root 'D:\work\project-a' --binding 'D:\work\project-a\binding-T01-v1.json' --kind STARTED --summary '已核对输入，开始执行'
python $helmScript publish --root 'D:\work\project-a' --binding 'D:\work\project-a\binding-T01-v1.json' --kind RESULT --summary '产物和自检就绪，等待主管验收' --report 'reports/T01-v1.md' --artifact 'output/result.json'
```

可用事件为 STARTED、MILESTONE、RESULT、BLOCKED、NEEDS_INPUT、NEEDS_APPROVAL、FAILED。只在实际状态变化时发布，不逐 token 上报。RESULT 自动记录报告和产物的 SHA-256；事件限 256 KiB，正文放报告。写入临时文件后原子发布到 `.session-helm/outbox/`，已存在事件不覆盖。

发布后，按真实用户授权用原生 `send_message_to_thread` 通知主管：项目、任务版本/attempt、事件ID、结论、待决定项和报告绝对路径。通知重试沿用事件，不另造 RESULT。完整报告就绪、原生消息送达、主管收到、主管验收分别记录；结束本轮等待，不循环询问或自行启动下一任务。

## 回报与审查队列

服务每秒扫描已注册 outbox；也可手动 `scan`。SQLite 事务和唯一事件ID处理并发：同一事件多次到达只入队一次，同ID异内容拒收。RESULT 仅进入 reported/queued，不能直接勾选完成。错误路由、旧版事件和拒收原因保留记录。

主管收到原生通知后先读取 snapshot，再领取：

```powershell
python $helmScript --db $helmDb --owner $helmOwner --epoch 1 claim
```

默认优先处理等待超过 10 分钟的报告，超时组按入队时间；其余先轮换项目，再优先审查能解锁更多直接后续任务的报告，最后按入队时间。必要时 claim --review ID 定向处理，说明原因。看板与 claim 使用同一排序。已有审查未结束时再次 claim 返回同一项，不能同时裁决第二项。先处理需要用户决定的输入/审批请求，再按队列审查。

领取后 focus 该项目，读取当前 Context、报告及实际产物，按任务标准独立检查。通过原生 wait/read 核实执行回合，并检查任务拥有的后台进程或持续写入；只有实际工作已停止，才记录 idle。当前任务版本、结果或规则变化会使旧 focus 过期；普通进度不影响它，裁决前须重新读当前包：

```powershell
python $helmScript --db $helmDb --owner $helmOwner --epoch 1 observe --project data --workflow main --task T01 --thread 'actual-executor-thread-id' --state idle --evidence 'native-snapshot-and-process-check-reference'
python $helmScript --db $helmDb --owner $helmOwner --epoch 1 review --review 'actual-review-id' --token 'actual-claim-token' --verdict accepted --evidence 'reviews/T01-v1.md' --note '独立检查及通过依据'
```

裁决前必须在本项目写独立 review 文件；不能引用执行者报告充当主管验收。accepted 重新检查当前任务版本、attempt、领取令牌、主管 epoch、前置验收、所有报告与产物哈希，以及独立观察到的 idle。写入完成才释放依赖。内容质量仍由主管核验，哈希相同不代表结论正确。

未通过用 needs_revision；缺输入用 waiting_input。临时切换项目先 release，然后 checkpoint。修改原任务范围用 revise 更新原卡 version+1；新增后续任务用 append（见[生命周期与交付](生命周期与交付.md)），保留变更理由，重新 prepare/bind；旧领取失效，下游绑定旧版本时显示待复核。不要重写旧报告或手工改数据库。

需要用户决定时，使用 request-decision --project ID --workflow ID --task ID --question 问题 --impact 影响 --option 选项A --option 选项B 登记。看板只显示，不批准；取得实际用户答复或核对已有明确授权后，把依据存入该项目，再 resolve-decision --decision ID --answer 答案 --evidence 项目相对路径。未解决的问题阻止对应任务派发和通过裁决；任务改版使旧问题作废。协议标识不等于用户身份认证，不可把执行者建议写成用户批准。

需要调整并发或积压上限时可用 limits --active 3 --reviews 4。降低上限只暂停后续派发，不拒收在途回报，也不会停止已有会话。不要直接修改数据库绕过限制。

## 自动看板与原生侧面板

```powershell
python $helmScript --db $helmDb serve --port 0 --ready-file 'D:\work\coordination\board-ready.json'
```

读取 ready 文件中实际 URL，用原生 `open_in_codex` 打开 `{target:{type:"browser",url:实际URL},placement:"right"}`。页面是 Codex 原生右侧浏览器面板承载的本地网页，不要求安装 MCP 插件。2026-11-11 已实测同一页自动变化，无需重新生成 Visualize；自定义 MCP 面板是另一种能力，不能混为已验证。

服务只监听 127.0.0.1，页面通过 SSE 收到序号后读取同一账本；断线重连补读 snapshot，不依赖一次性广播保存事实。项目卡片数据未变则保留原节点、筛选和展开状态。界面显示任务与依赖、按实际优先级排列的队列及等待时间、待决定问题/影响/选项、主管当前项目、验收数和运行核实时间。主管提交验收后自动出现勾选。

报告和独立审查记录可点击，只提供当前绑定且哈希一致的文件，以纯文本打开；不提供任意文件浏览。会话 ID 可复制，当前普通网页没有原生导航工具桥，不能把复制按钮称为一键打开对话。需要打开对话由主管使用宿主已提供的 navigate_to_codex_page，调用仍遵守用户意图。

页面记录可见时从账本变化到两次 animation frame 后的呈现延迟，最多保留 200 个当前页面样本；重连补发与实时变化分开。页面隐藏或重载后不拼接成连续测量。该数据用于核验本机 5 秒更新目标，不代表网络分布式时延承诺。进度按里程碑和验收数表达，不虚构百分比或把服务心跳当作执行进度。

服务和页面持续运行时，执行者发布事件即可更新看板，不需要主管启动新模型回合。主管回合休眠时，**入队和显示可以继续；审查、派发后续任务仍需主管被原生消息唤醒或用户续接**。服务不提供网页写接口或任意文件浏览，也不从网页批准任务。

需要后台启动时用隐藏进程并保存 PID、开始时间和完整命令行；不得只凭端口号或相同名称结束进程。停止前台服务用 Ctrl+C；后台停止只针对核实属于本次运行的进程。关闭面板不代表服务停止，关闭应用期间是否运行或恢复不能由一次面板测试推定。

## 恢复、交接与兼容

- 服务重启：使用相同 db；历史事件、审查队列和序号保留，重复扫描不会重复裁决。
- 主管更换：原主管执行 `handoff --to 新主管真实ID --reason 理由`；epoch 增加，已领取的报告回队，旧主管/旧令牌失效。新主管读取 snapshot 与计划，再核实真实会话后继续。
- 原生回报未到：outbox 仍可采集；主管用队列恢复。服务未运行：事件仍在文件中，启动或 scan 后补收。不保证服务自己唤醒主管。
- 执行状态未知、停止或应用重启：按[停止与重启验证](停止与重启验证.md)分别检查回合、进程和输出；不要用 observe 伪造 idle 释放占位。
- 首版只支持同宿主本地目录；跨机器 outbox、账号权限隔离和常驻自主调度不在这个运行模式的保证内。
- 经典状态可用 `export --project ID --workflow ID --output 项目内派生state.json` 后交给 `helm.py`。该导出只读，不能再导回或手改冒充账本。

参考思路：Paperclip 的持久回报与审查边界、Agent Orchestrator 的事件日志及实时视图。具体实现保持轻量，不引入它们的完整平台；本地证据与现场工具能力优先于上游项目功能描述。
