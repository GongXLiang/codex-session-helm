# 按任务选择模型与思考强度

主管在派发或追加实质任务前自动评估。用户明确指定的模型、强度、预算和“沿用默认”优先；只固定一项时，其余项仍可按任务选择。选择不改变当前主管自身的模型，也不自动创建会话。

## 1. 先评估任务，再选择配置

主管从真实任务卡、输入和验收条件判断以下四项，各记 0、1 或 2，并留一句依据。信息不足时先补读相关输入，不把未知一律记为 0，也不要求用户自己填评分表。

| 项目 | 0 | 1 | 2 |
| --- | --- | --- | --- |
| 不确定性 ambiguity | 方法、目标和输入明确 | 有少量实现选择 | 原因、方法或关键假设未定 |
| 依赖复杂度 coupling | 单项独立工作 | 多文件但关系明确 | 跨模块或多阶段相互影响 |
| 出错影响 consequence | 局部、容易恢复 | 会影响交付但可复核修正 | 关键结论、重要数据或难以撤回的决定 |
| 验证难度 verification | 有明确自动检查 | 需要内容或视觉复核 | 缺少可靠判据或有相互冲突的证据 |

三档规则是本项目的调度启发式，不是模型能力评分：

- **简单**：四项全为 0，优先 focused 类模型，采用该模型适合此类任务的基准强度。
- **常规**：其余未达复杂条件的任务，优先 general 类模型，目标强度 medium。
- **复杂**：出错影响或验证难度为 2，或四项总分至少 5，优先 deep 类模型，目标强度 high。
- 写作、图表理解或界面操作可标记 kind=visual；简单／常规任务优先 visual 类，复杂任务仍按复杂档处理。

任务长短、文件数量、主管／执行者名称都不能单独决定档位。简单格式转换不会因为材料很多自动变成复杂任务；一句很短的关键结论核查也可能属于复杂任务。

## 2. 从现场可用模型中匹配

每个宿主首次使用时，读取实际工具描述或模型列表，登记可用模型 ID、支持的强度、默认模型（可确认时）和覆盖限制。同一轮复用这份记录；换宿主、模型拒绝或工具变化时重新发现。

按已核实的能力给模型分配 focused / general / deep / visual 角色，同一角色的候选按偏好顺序排列。2026-11-11 的示例对应关系是 Luna、GPT-6.1 Sol、Astra、GPT-6.1 Terra；这些是示例，不是永久名称或账号可用性保证。未核实的新模型不只凭名字更大就替换。

基准强度按模型记录，不能把不同模型的 low/high 当成同等能力。例如示例中 Luna 的简单任务基准为 high，Astra 为 low，Sol 与 Terra 为 medium；后两项是本项目起始策略，不冒充宿主默认值。复杂任务的 high 是本项目选择，后续根据实际验收调整。

用户限定可用模型时只在该集合内选择。首选角色缺失时，使用集合内已确认的当前默认模型，并记录缺口；默认也未知时保留推荐、不猜实际配置。用户明确指定但不可用的模型或不支持的强度，应说明冲突，不悄悄换一个近似值。

自动强度默认不超过 high；用户可配置上限为 low / medium / high / xhigh。目标档位不支持时取不超过目标和上限的最高受支持档位。max、ultra 只接受用户明确指定；不得为自动提速引入额外代理。没有可用档位或宿主不能控制强度时，不自动换到默认强度未知的另一模型。

## 3. 推荐、调用参数、实际运行分别记录

为当前操作读取工具限制，而不是假定所有桌面工具相同：

| model_policy | 参数处理 |
| --- | --- |
| allowed | 在用户本次任务范围、预算和工具规则内传入自动选定的 model |
| explicit_only | 只有真实用户明确指定具体模型时才传 model；“请自动选择”本身不等于指定了某个模型 |
| unsupported | 不传 model；用户要求覆盖时报告能力冲突 |

2026-11-11 的 create_thread 属于 explicit_only。不要先用默认创建再补发换模型来绕过这个限制。fork 未暴露模型参数时也不能在提示词里声称已经切换。对已有会话的后续操作按该操作的实际规则处理，不能从创建接口或旧回执推定权限。

`thinking` 必须针对实际将运行的模型校验。若推荐 Luna 但宿主只能继承 Sol，应重新按 Sol 计算；实际默认模型未知时省略自动强度覆盖。用户明确指定强度却无法核实目标模型时，先解决这一配置缺口。

调用成功只记为“参数已接受”。能从宿主回读本轮实际配置时，记录生效模型、强度与依据；回执没有这些字段时记“实际配置未回读”。执行者自述“我是某模型”不算证据。不改全局配置或另开运行环境来代替单个会话选择。

任务卡和既有执行状态中保留：评估依据、用户固定项、推荐 model/thinking、实际提交的覆盖字段、未应用原因，以及运行配置的核实状态。只有决定有变化或受工具限制时才向用户说明，避免每个任务重复询问。

## 4. 返工时调整一次，并保留用户约束

验收失败先分类。缺输入、权限、依赖或环境故障先解决对应问题，不能靠更强模型掩盖。确有推理不足时，可依据失败证据重新评估，在下一个获准执行回合调整配置；用户固定的字段不动，自动上限不突破。共享状态记录调整次数，同一派发版本最多自动调整一次；没有可用的更合适配置或再次失败时，报告具体证据和待决定项，不循环升级或重跑已验收部分。

Fast 是独立的速度与用量设置，不作为思考强度档位。沿用用户现有设置；当前桌面会话接口没有 fast 字段时不生成此参数、不修改全局配置。用户明确要求速度优先时可提出建议，只有实际接口及授权支持才应用。

## 5. 可选的参数检查器

`scripts/model_router.py` 使用 Python 标准库，输入主管已评估的任务和现场能力快照，输出确定的推荐与可传参数。它不理解原始任务文本、不发现模型、不调用会话工具；自动评估和派发由主管按上面的流程完成。

```sh
python scripts/model_router.py examples/model-routing.json
python -m unittest discover -s tests -v
```

示例是可复现输入，不是本机实时配置。实际使用时在项目任务目录生成请求，不覆盖仓库示例。JSON 字段如下：

- `schema_version: 1`；`assessment` 含四项 0–2 分及 `kind: general | visual`。
- `models`：每项有 `id`、`roles`、`efforts`、`baseline_effort`；基准必须在支持列表内。候选顺序表示同类偏好。
- `default_model`：当前操作实际继承的模型 ID，未知为 null；不能拿官方推荐值填成用户默认。
- `model_policy`、`thinking_allowed`：从当前操作的真实工具限制填写，不能为获得期望结果修改它们。
- `mode`：auto 默认自动选择；inherit 保留现有模型和强度，仍可单独指定 user_effort。
- `user_model`、`user_effort`：只填写真实用户明确固定的值，未指定为 null。
- `allowed_model_ids`：可选的用户允许集合；null 不额外限定。`max_auto_effort` 默认 high，仅约束自动选择，不覆盖用户明确强度。

输出中 `recommended` 是选择建议，`target` 是按宿主规则推导的请求目标，`overrides` 才是可供当前工具调用的覆盖字段。`runtime_verified` 始终 false，因为检查器没有运行会话。目标模型未知时不会生成依赖该模型的自动强度参数。退出码 0 表示参数准备完成；2 表示输入、用户约束或宿主能力有冲突，不能继续使用半套输出。

依据：[OpenAI 模型说明](https://learn.chatgpt.com/docs/models)、[速度设置](https://learn.chatgpt.com/docs/agent-configuration/speed)。模型角色和默认建议会变化，实际工具能力与用户设置优先。
