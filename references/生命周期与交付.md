# 持续追加、归档、预审与项目交付

以下功能需要 schema 3。旧 schema 1/2 账本先停止对应服务/写入者，用 `upgrade --backup NEW_FILE` 保存一致性副本；升级保留任务、回报、摘要和历史，清除旧 focus。备份文件不得已存在。不要手工改表绕过校验。

## 追加与归档

`register` 只登记新项目。对既有项目先写新增卡片，必要时 save-context 登记新规则及来源，再加载项目 focus：

```sh
python scripts/helm_runtime.py --db DB --owner OWNER --epoch 1 focus --project P
python scripts/helm_runtime.py --db DB --owner OWNER --epoch 1 append --project P --workflow main --tasks new-tasks.json --expected 1 --reason "依据上一轮结果新增后续工作"
```

`new-tasks.json` 使用 `{"tasks":[...]}`，每项沿用[任务格式](../examples/demo-state.json)，必须 version=1、planned/unknown。每次追加 1–100 项。`expected` 为工作流 generation，可从 portfolio/snapshot 读取；新工作流填 0。重复 ID、缺失或循环依赖、越界写路径、旧 generation 使整次追加回滚。任务依赖仍限同一工作流；跨项目先用明确产物交接，不伪造直接依赖。

```sh
python scripts/helm_runtime.py --db DB --owner OWNER --epoch 1 archive-workflow --project P --workflow main --expected 2 --summary "本阶段已验收，保留交付入口"
python scripts/helm_runtime.py --db DB --owner OWNER --epoch 1 restore-workflow --project P --workflow main --expected 3 --summary "新需求进入下一轮"
```

每次操作前重新加载项目 focus。归档要求所有任务有效验收、实际 idle、产物哈希一致，且没有未结审查、派发意图或决策。归档仅移出活跃任务视图，事件、回报、审查和产物均保留；`list-tasks --include-archived`、`export` 可查历史。恢复增加 generation；若归档后证据改变，允许恢复修复，但不会重新认证旧产物。恢复后才能追加或修订。这里是账本工作流归档，不会自动归档桌面对话。

## 按任务加载与差量读取

`focus --project P --workflow W --task T` 的变化校验只覆盖目标、完整依赖链及相关决策；普通 MILESTONE 和无关任务结果不使它失效。任务改版、attempt、验收/结果状态、来源规则变化仍使它失效。任务级 focus 不能授权另一个目标，也不能用于项目级追加、归档或交付写入。

规则摘要完整保留；可见任务最多 12 项，清楚返回 omitted 数量。`list-tasks` 每页最多 50 项，细节通过任务卡和报告读取。增量 `--delta` 仅用于同一主管 epoch、同一范围，返回变化字段及任务；压缩恢复、换主管或不确定是否还记得前一包时重新加载完整包。它控制输入材料，不会擦除模型历史。

## 并行预审与唯一裁决

```sh
python scripts/helm_runtime.py --db DB --owner OWNER --epoch 1 record-precheck --review REVIEW_ID --reviewer REVIEWER_THREAD --evidence reviews/precheck.md --note "独立测试范围与结论"
python scripts/helm_runtime.py --db DB --owner OWNER --epoch 1 next-review --review REVIEW_ID
```

主管登记真实独立复核会话提供的材料，reviewer 不能是主管或当前执行者。来源身份仍须主管从原生回执核实，字符串不是身份认证。预审不自动抢占或放行任务，最终 review 仍重新校验版本、idle、依赖和产物。预审证据有改动则标为无效，任务改版使旧预审不再出现。一个预审者对同一次 review 登记一次，需补正时保留原报告并让主管在最终验收说明差异。

## 项目交付单独验收

```sh
python scripts/helm_runtime.py --db DB --owner OWNER --epoch 1 set-gate --project P --id gui --title "真实界面交互" --state pending --reason "尚未实际操作验证"
python scripts/helm_runtime.py --db DB --owner OWNER --epoch 1 set-gate --project P --id release --title "独立交付" --state passed --reason "按标准独立核验通过" --evidence reviews/release.md --task-ref main/T05
```

通过项必须提供独立证据和已验收任务绑定；证据或绑定任务变更后显示 needs_recheck。项目只有存在交付项、全部通过且没有未完成任务时才显示交付通过；没有定义标准时显示 undefined。即使所有任务勾选或工作流归档，GUI 等 pending 项仍显示待验证。界面每 15 秒重读证据状态，账本写入通过 SSE 自动刷新。

## 采集与开销

服务仍每秒枚举各项目 outbox，未改且已处理的文件使用进程内 stat 签名缓存，避免每秒重复哈希和写事务。变化、重启、60 秒周期复核或 `scan --verify` 会重新哈希。未部署文件系统监听，不承诺零 I/O；单次 CLI 进程无法复用前一进程缓存。事件记录和内容哈希仍是去重依据，缓存不是权威数据。

角色入口、任务工作集、差量 focus、next-review 可以减少重复文字和调用；字符数/调用数并非 Token 或费用实测，不能据此宣称固定节省比例。

## 设计参考

借鉴 [Paperclip 的 heartbeat 协议](https://github.com/paperclipai/paperclip/blob/master/docs/guides/agent-developer/heartbeat-protocol.md)中任务归属、冲突停止和持久下一步，以及 [Agent Orchestrator](https://github.com/OrchestratorInc/agent-orchestrator)中主管汇总多个执行者、区分执行与审查状态的思路。本实现保留本地文件、SQLite 与宿主原生会话接口，没有复制其代码或引入平台依赖。
