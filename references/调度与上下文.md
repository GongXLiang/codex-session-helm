# 调度与上下文

任务增多、等待浪费或反复返工时读取。优化目标是减少无效工作和上下文占用，不以会话数量作为产出。

## 1. 按任务选开销

- 单步修改、解释和局部检查：留在当前会话，不创建编排文件。
- 有独立交付物的小任务：使用[简版任务卡](../assets/简版任务卡.md)，复用项目已有状态入口。
- 多阶段研究、多人写入或长时间任务：完整任务卡、依赖版本、独立验收和恢复记录；需要时启用[状态检查与看板](状态与看板.md)。

主管读取当前状态、相关裁决、输入证据与待验收产物。执行者只读取自身最新任务卡、必要输入和前置验收摘要。复核者读取验收条件、原始证据与实际产物；尽量先独立判断，再对照执行者解释。不要把主管全部历史复制给每个执行者。

同一宿主同一轮工作复用已核实的能力记录、授权定位和项目入口；工具缺失、升级、状态冲突或权限报错时才重新探测。能力缓存不能替代派发前的当前状态核对。模型和环境沿用用户设定，不擅自为了“提速”换模型。

## 2. 选择下一批

1. 处理已送达报告、当前版本与独立验收，更新权威状态；候选仅为尚未派发、没有实际运行的任务。
2. 检查每个前置任务均为当前有效验收版本。报告完成、回合结束、等待输入、暂停和解除关联都不能开门。
3. 核对实际工作区和写入范围。同一个文件、父子目录、大小写别名、符号链接或目录联接不能被误认成互不相关。无法可靠拆分时串行或在用户允许的独立工作区执行。
4. 按用户指定的并发上限减去当前仍在运行的任务；暂停标签不释放实际仍运行的进程。优先已有明确优先级、能解除更多后续阻塞的任务；这是启发式排序，不是基于工期的最优排程。
5. 发送前核查已有会话、送达记录、当前版本与授权。发送成功先登记回执；不因为暂未看到输出就重复创建或重发。

独立只读检查可以批量并行；写同一状态、审批、修订和依赖动作顺序执行。等待使用当前 cursor 和有界 wait_threads；紧凑快照够用时不重复读取全历史。不为每条消息再发“收到”触发来回唤醒；仅在需要裁决、补充输入或交接确认时回复。

## 3. 上游变化怎样传递

依赖保存为任务ID和实际采用的版本，例如 T01@2；不能仅写“依赖T01”。上游更新版本或撤销验收时：

1. 保留旧报告和裁决，标记直接引用它的任务及传递依赖为待复核；暂停这些结果对决策门的支持。
2. 检查实际影响：输入或定义改变则重新执行受影响部分；只有措辞变化且证据不变时，可复核后保留结果。不要不加判断全部重跑。
3. 写明采用新版本的依据、保留／重做范围和新的验收记录，再更新依赖版本。不能只把引用数字改为最新版来消除告警。
4. 对已运行的受影响任务单独决定继续、暂停还是改版。新任务卡送达不等于旧运行已停止；先核对运行与文件冲突。

只读检查器提供待复核提示，不自动改变任务版本或替主管验收。任务卡正文、状态和验收入口必须指向同一有效版本。

## 4. 评估优化是否有效

对实际工作记录必要的派发、首次开始、回报、验收时间与返工原因。只在存在问题时看等待、重复读取、重复运行和验收耗时；优先消除最大的浪费。没有对照测量，不宣称固定百分比提速。停止、重启、跨环境的行为测试分别记录，不能从脚本检查通过推断桌面生命周期通过。
