# 能力边界与最小验收

在首次使用新宿主、升级工具或承诺自动续接前读取。这里区分公开文档、现场工具 schema、实际行为测试和未验证事项；同名功能不自动等价。

## 1. 能力检查

先发现当前工具并记录宿主与可用操作：创建、fork、发送、读取、等待、分组、停止、归档及工作区隔离。create_thread 返回真实 threadId 后才测试后续动作。侧栏 API 不等于嵌套生命周期 API，协议里的父子字段不保证可设置任意任务关系。

工具不可用时报告具体缺口；可以继续准备任务卡、验收方法和手动续接说明。只有原生能力确实不能满足已授权目标时才提出薄适配器，不自行启动另一套 App Server 并假定能接管桌面活动会话。

## 2. 分层验收

| 检查 | 有效证据 | 不能据此声称 |
| --- | --- | --- |
| 接口存在 | 现场工具定义或本机导出的 Schema | 桌面实际联动成功 |
| 创建与分组 | 返回真实ID，列表读回成员和顺序 | 折叠已验证、具有原生父子关系 |
| 主动回报 | 执行者真实发送，主管原先空闲，随后出现新回合并读取报告 | 应用退出后仍保证唤醒 |
| 忙碌时消息 | 发送时目标active，后续读回相同事件及处理证据 | 所有并发量与宿主都不会丢消息 |
| 旧版和重复回报 | 真实版本记录、通知、主管裁决与产物对照 | 仅检查字符串格式就验证了去重 |
| fork | 对指定源fork后读回实际历史、文件环境和是否启动 | fork隔离了文件、继承了全部隐含配置 |
| 停止／归档／恢复 | 对隔离目标执行，核对真实状态与产物保留 | 停止消息立即中断、归档没有连带影响 |
| 重启恢复 | 获授权重启宿主后核对状态与通知 | 仅从文件恢复一次就证明宿主重启不丢事件 |

普通任务只做与风险相称的检查。开发本工作流时使用专用测试组和临时目录；测试提示保持真实、可读，消息附人类授权来源。默认不为验收关闭有其他工作的应用，不碰既有项目会话，不把测试通过自动记入项目认可成果。

## 3. 行为用例

1. 两个独立任务乱序回报，只有必需的当前版本全部验收后才执行依赖步骤。
2. 同一逻辑结果重复通知、旧派发版本晚到，都不覆盖有效状态或重复推进。
3. 执行者需要输入、审批或被中断，回合结束不被判定为成功。
4. 回报投递失败或状态不明，保留文件并查证；不盲目重建会话或反复发送。
5. 主管在新回合从状态文件恢复，不重新运行已有有效成果；主管更换后只有一个当前责任人。
6. 显示移组不改变依赖；解除关联的未完成任务不会悄悄满足决策门。
7. fork、停止和归档分别验证，精确记录真实影响范围。应用重启、跨主机、云端另测。

- [Desktop 会话任务卡](https://code.claude.com/docs/en/desktop#start-a-task-that-claude-suggests)及[跨桌面会话](https://code.claude.com/docs/en/desktop#work-across-sessions)：公开用户流程。
- [Claude 跨会话消息](https://code.claude.com/docs/en/cross-session-messaging)：另一消息通道的投递、通知和限流，不直接当作 Codex 或 Desktop 专用通道规则。
- [Codex App Server](https://learn.chatgpt.com/docs/app-server)：线程、回合、事件和section协议；实际可用性仍核对宿主。

用户提供的 Claude 会话工具／提示快照属于版本线索。固定预览长度、提案数量、自动唤醒例外和detach细节未经当前验证，不写成跨产品常量。第三方界面记录用来寻找入口，不替代本机验收。

## 5. 当前验证记录

验证日期：2026-11-11。环境为 Windows 本地 Codex 桌面原生会话工具；本机 CLI Schema 版本为 0.167.0，不能据此推定桌面客户端版本。具体会话 ID、报告和检查快照保存在本次升级验收记录，不固化为 Skill 的运行地址。

已实测：

- 创建独立主管和两个执行会话；真实 ID 可寻址。创建时标题有未保存的情况，经 set_thread_title 后读回正确。
- 主管置顶、执行者自定义分组、全量成员排序和移组；这些证明组织操作，不证明折叠按钮或审批请求自动显露。
- 一次 sectionId:null 的移出调用返回成功，但随后仍读到旧组成员；显式 sectionId:"chats" 后读回已移出。运行时必须复核实际结果。
- 主管到执行者的派发与修订、执行者回报唤醒空闲主管、主管忙碌时收到并处理其他报告。此处只覆盖本地测试中的消息量和交错顺序。
- 两项有效报告独立验收齐备后才生成下游；旧版本、重复通知及返工后再到达的旧报告均未覆盖有效结果。
- NEEDS_INPUT 阻塞报告被正确识别：执行者回合结束不等于任务完成，未满足依赖未放行。
- 同一主管的新回合按实际文件恢复，已生成下游文件的 SHA256 与最后写入时间保持不变。
- 接收方先核对并确认、原主管释放职责后才激活新主管；有效版本、去重事件和未完成依赖随状态接续，来源快照保持不变。工作流层解除关联后，任务仍记为未完成，下游仍阻塞；向新主管重投原阻塞通知后，只登记迟到事件，没有恢复调度或重复推进。
- 对空闲会话进行 same-directory fork，读回继承历史及相同工作目录；未发新任务时没有自行重跑。叶会话归档、恢复后历史仍可读取，原执行会话仍在活动列表。归档后的 ID 可能保留在 section 成员记录，恢复后可能显示 notLoaded。
- 归档本次普通 fork 的来源会话后，fork 会话仍在活动列表，没有观察到连带归档；仅限本次创建方式与宿主。最终逐项核对四个测试会话均已归档、测试分组已删除，历史与本地报告保留。

新增真实停止实测（客户端包26.1103.7773.0）：用户点击测试会话停止后，原回合读回 interrupted；但其 exec_command 启动的 Python 进程（PID及创建时间均匹配）仍写入，两个停止后快照的计数由160增至182。核对归属后显式结束该专用进程，文件保留。结论是“回合中断有效，进程未随之自动停止”；不能宣称一键停止全部工作。同一会话随后按检查点只补做183、184两步，主管独立确认原182步字节未变、无重复或缺失；该项是停止后的续接，不是应用重启。恢复规则与复测方法见[停止与重启验证](停止与重启验证.md)。

停止复测（2026-11-11）：首次停止后曾出现用户发起的后续回合，因此另用全新输出目录复测，用户仅点击一次停止，之后不接受建议、不输入消息、不继续执行。原测试回合读回 interrupted，两次观察后仍是同一个回合，没有新的后续回合；原Python进程的PID与创建时间始终匹配，停止后的记录由44增至71，随后仅对该已核实进程作显式清理。此次排除了后续会话操作的干扰，仍复现进程继续运行。测试具体覆盖 exec_command 启动命令并返回 session_id、再用 write_stdin 等待的本地场景；不据此断言所有工具、启动方式或宿主都有相同行为。

应用重启实测（同一客户端包）：用户正常退出并重开，主进程身份及启动时间确实变化。原测试会话起初显示 notLoaded，但可读取原历史及最后完成回合。重启前已有产物的哈希、写入时间和检查点保持不变；向原会话发送续接任务成功，执行者只新增185、186两步。主管独立核对原184步逐字节保留、无重复或缺失，原已验收产物内容与时间不变，新回合正常完成。该项证明重开后依检查点续接，不证明关闭期间运行、消息保证或自动唤醒。

仍需单独验证：折叠／展开及阻塞请求自动显露、长期后台及关闭期间消息、跨主机和云端、worktree 隔离、真实审批事件、多层委派、投递丢失与高并发压力。当前没有发现可直接折叠或停止的原生桌面工具；不得因本地消息测试成功而声称这些能力已支持。交接和解除关联按工作流记录实现，不声称已改变原生父子关系或取消宿主回调。

## 6. 第一版基础联调记录及口径更正

2026-11-12 更正验收口径：2026-11-11 完成的是同一 WIKI-vault 工作区内的三组演练任务联调，分别为数据核对、时长解析工具和发布说明编辑。它们分别登记了逻辑项目ID、目录、计划、任务卡、产物、报告和 outbox，使用三个真实执行会话；但均服务于同一次 SessionHelm 升级测试，任务短小，没有覆盖三个无关项目各自持续规划、多轮执行与交错调整的实际使用场景。因此，原先“完成三个独立项目真实验收”的结论过度，应改为“基础联调通过，真实多项目综合验收尚未完成”。

- 三个真实执行会话各执行 T01，回报按逻辑项目ID分开入队；主管忙碌时收到了三条原生通知。这证明了本次演练的路由与队列行为，不能据此推定长期多项目上下文不会混淆。
- 数据项目 T01 的9条输入中，7条有效、总额220.00；主管独立复算和运行检查通过。T02 在 T01 未验收时被拒绝派发，验收后由原会话完成摘要并再次验收。
- 代码任务 v1 满足原卡后，主管在演练中模拟需求变化并升级 v2。旧领取令牌无法裁决新版，重放原 RESULT 返回 duplicate；原会话使用新绑定完成 v2，主管重跑8个测试方法并额外检查21个边界样例，旧产物哈希不变。这不是用户在真实项目中临时改计划的现场验收。
- 写作项目的161个汉字发布说明经过主管逐句来源核对，准确区分回报、验收和自动刷新条件。
- Codex 原生右侧浏览器面板显示本地页面；同一页面从0/4变到2/4、最终4/4有效验收，期间状态变化没有手动刷新。项目筛选、依赖图、待审查队列和验收勾选均实际观察。
- 本地看板服务重启后，账本序号与两份待审查报告保留，原页面在同一URL自动重连。重启的是本次看板服务，不是Codex应用；不据此扩大应用关闭期间的保证。
- 最终4项演练产物按各自任务卡验收通过，0项待审查、0个未对账的派发意图；三个执行会话为空闲，保留一个只读看板服务。原生分组成员经list_threads读回核对。看板4/4表示这些演练任务的状态，不代表首版升级全部验收通过。

63项自动测试中，45项属于原有检查器及模型选择，18项属于新增账本与服务；它们覆盖并发去重、事件ID碰撞、改版和交接防护、产物变化拒绝验收、审查串行领取、积压限流、目录冲突、错误/超大事件隔离、服务只读端点和SSE重连。自动测试与桌面联调分别记录，不能代替真实多项目综合验收。

第一版结束时尚待完成的验收：三个无关项目各自具有独立目标、规则、计划和多轮任务，并在同一主管下持续交错推进；新账本模式下真实主管中断及更换后的续接；入库后5秒内更新的计时检查；审查积压与项目处理机会的实际负载检查；用户受打断次数、审查等待时间、重复运行及错误发现情况的效果评估。后续实测见第 7 节，不能用后来的结果倒改第一版记录。

第一版的简化实现：审查队列当时仅按项目轮换和等待时间选择，没有下游解锁排序；看板只有状态、路径和会话 ID，没有证据打开入口或结构化决定选项；上下文包当时只有文件路由。这些历史缺口的本轮进展见下节。所有版本均不能自动清除模型已读的聊天历史。原生右侧浏览器承载本地网页已验证，独立 MCP App 路线未实现。

## 7. schema 2 与三个独立项目的多轮验收

2026-11-12，同一 Windows 本地宿主，使用三个新建且相互不依赖的项目目录、项目规则、计划、产物与原生执行会话。SplitLedger 为整数分费用分摊 CLI，VaultCheck 为 SHA-256 归档核验 CLI，RecallDeck 为离线学习 HTML。每个项目均经历初版、反馈修订、独立打包三个阶段。共记录 11 次实际派发：9 个当前阶段，加费用项目的需求改版和卡片项目的验收范围修订各一次。保留 1 份被新版替代的审查和 1 份因 GUI 未验证而等待输入的原始审查。

已验证的运行行为：

- 多项目全局摘要与单项目上下文分开；真实派发中，无 focus、未保存检查点切换项目、在另一个项目下派发、前置未验收均被拒绝。新摘要带项目内来源哈希和版本；过期源文件、并发版本覆盖、过期裁决等边界另有自动回归。它是操作门禁和文件路由，不是模型历史清空或操作系统访问隔离。
- 三个执行会话确实同时运行并交错回报。持久化事件重复两次仍只处理一次；审查中修改费用项目的唯一 id 要求后，旧 token 裁决被拒绝，迟到旧回报只记为 stale，另两项目的计划和定义未被更改。需求变化是明确标识的验收演练。
- 审查队列实际按项目轮换及解锁下游排序；真实待审积压达到临时设置的 2 项阈值时拒绝继续派发，随后恢复默认 4 项并继续。10 分钟老化优先规则通过合成时间测试，不能把它称为长期生产负载验收。
- 一个没有继承主对话历史的新主管会话，仅凭全局摘要、项目上下文、原始报告和文件接手 VaultCheck 初版的独立审查，再交回原主管；epoch 从 1 到 2 再到 3，旧主管和旧领取令牌失效。接手者独立运行 29 条断言及 14 次 CLI。它的一次跨会话回告被自动审批拒绝，主主管从账本和原生状态读回结果，完成续接；不能承诺每次主动通知都能唤醒主管。
- 看板在 Codex 原生右侧浏览器中从执行、待审推进到当前 9/9。最后一次验收时只有 RecallDeck 卡片重绘，另外两张项目卡保留原 DOM；报告和独立验收入口可打开，问题、影响、选项可结构化展示。当前任务全部打勾不代表 GUI 缺口通过。
- 在可见页面记录 119 个去重的在线变化样本，从账本审计时间到双 requestAnimationFrame 后的 DOM 呈现，中位数 524 ms、最大 1,022 ms，均小于 5 秒。该指标不含模型执行时间，也不等于操作系统像素显示延迟。断线重放样本单独排除。真实停止并重启看板服务后，原页面同一 URL 自动重连，补齐断线期间变化；未知执行状态仍保持未知。
- 将真实第一版账本复制后显式升级，3 个项目、4 个任务和原裁决保留，一致性备份保持 schema 1；原账本未修改。旧 schema 1 本身没有新上下文门禁，须显式升级。

独立交付验收：主管重新解压三个最终 ZIP。SplitLedger 的 18 项测试和额外手算/CSV/坏输入检查通过；VaultCheck 的 20 项测试及独立 CLI 检查通过，包含本机真实 ACL 与目录联接；RecallDeck 的 20 项核心及模拟交互测试和额外核心边界检查通过。两个 CLI 在本机可独立使用；未把目录隔离等同于新机器或其他操作系统已验证。

同步到已安装 Skill 后，完整 72 项 unittest 通过；原有示例及文件检查、看板 JavaScript 语法、git diff --check、Skill 格式验证均通过。72 项包含原有 45 项检查器/模型选择、18 项基础账本/服务和 9 项新增主管上下文回归；这个总数不包含三个演练应用的测试。没有把本机回归称为 GitHub CI 或跨平台运行通过。

**RecallDeck 原完整界面验收未通过。** 原生内置浏览器拒绝 `file://` 自动化访问，用户选择延后界面验收；随后用户主动授权，正式文件预览虽可打开，自动化仍拒绝该协议。原始等待输入记录保留，后续任务显式改为核心范围并带“GUI 待验”。本地打开、下载导入、刷新持久化、键盘及窄屏仍未实测，不能用 Node 模拟交互代替。

负担记录：本轮主动询问用户 2 次（选择项目、界面阻断处理）；用户另主动授权访问 1 次。11 份审查从收件到裁决的经过时间中位数约 172 秒、范围约 140–958 秒，包含主管同时开发和核验的时间，不是纯审查工时。没有对照组，不能声称提高了多少效率。结构化决定卡的展示使用明确标记的演练问题，不把演练选项当成人类新授权。
