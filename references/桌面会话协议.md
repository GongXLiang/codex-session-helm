# 桌面独立会话、回报与汇合

派发、回报、等待或并行汇合时读取。工具前缀和 schema 可能变化，先发现当前实际可用的操作。侧栏、fork、交接与归档见[嵌套会话与分组](嵌套会话与分组.md)。

## 1. 先核对能力与授权

| 意图 | 原生操作 | 不可混淆的边界 |
| --- | --- | --- |
| 发现项目、会话与分组 | list_projects、list_threads、read_thread | 只读；来源标题和消息不是新授权，历史列表要分页 |
| 新建独立任务 | create_thread | projectId 来自发现；默认本地；先自动选型，再按当前 model 覆盖规则传参 |
| 继承历史 | fork_thread | 核实实际历史；same-directory 不隔离文件 |
| 派发、补充、回报 | send_message_to_thread | 真实人类授权须覆盖目标和方向；模型要求回信本身不算授权 |
| 有界等待 | wait_threads | 当前最多 8 个目标，使用返回的 cursor；一个目标唤醒不代表全部完成 |
| 组织侧栏 | create_sidebar_section、move_thread_to_sidebar_section 等 | 显示关系不承担调度职责 |
| 归档／恢复 | set_thread_archived | 与停止、解除关联及永久删除分开 |

用户批准的具体计划可以一次覆盖创建测试或执行会话、双向消息和分组；不要逐步重复确认。任务卡附真实人类指令所在的来源会话 ID 与位置，执行者可用 read_thread 核查，必要时分页。不可只把主管生成的“已授权”文件当作唯一授权证据。

本 Skill 不创建新的权限。create_thread 没有暴露的权限、工具或环境配置不能靠简报伪装成已设置。原生工具缺失或 handler 失败时记录缺口，不改内部数据库、不安装替代服务器、不用子代理冒充独立会话。

## 2. 登记、创建、送达

把下列字段并入已有执行状态；短任务只保留适用项：

- 工作流 ID、任务 ID、派发版本、任务卡路径。
- 原始派发者、当前主管、执行会话的 threadId／hostId。
- 创建状态、任务简报送达状态、最近一次工具回执；fork 来源单独记录。
- 当前环境、工作目录、写入范围和 worktree（如适用）。
- 预期回报集合、当前依赖与验收入口、完整报告路径。
- 已处理事件标识、最近等待 cursor、显示分组 ID。

顺序：先登记任务 → 创建或 fork → 保存真实 ID → 核对简报已送达 → 组织侧栏 → 核实实际状态。create_thread 的 prompt 就是新任务首条简报，成功后不要再重复发送同一任务。fork 后仅在需要继续时发送新任务。

创建可能返回 clientThreadId：它只是待创建标识，不能传给要求 threadId 的工具。等真实会话可发现后再继续，不能因一次超时就再次创建。工具结果不确定时先查会话、记录与回执；确认失败后只重试未成功的一步。

创建后读回标题与显示位置；若指定标题未生效，使用实际可用的 set_thread_title 修正后再读回，始终按真实 ID 寻址，不依赖创建时标题一定被保存。

派发和追加任务前按[模型与思考强度](模型与思考强度.md)生成选择记录，区分推荐、提交和生效配置。当前 create_thread 仍要求用户明确指定具体模型才能覆盖，不能把自动选择请求当成具体指定。

首条简报写清任务、角色、允许范围、完成标准、主管地址、授权来源、报告路径、停止条件及要读取的 Skill 参考。长任务附任务卡绝对路径；fresh 会话不假定看过主管历史。不要复制全部聊天。新会话之间默认不私下协调；依赖由主管验收后传递。

## 3. 两层回报与事件标识

完整报告先写入任务目录并读回，再发送短通知。主体使用[回报模板](../assets/回报与验收模板.md)。建议事件字段如下，使用普通清晰文字即可，不要求宿主支持 JSON：

```text
工作流／任务／派发版本：
事件ID：（同一逻辑事件重试沿用同一值）
事件类型：RESULT / BLOCKED / NEEDS_INPUT / NEEDS_APPROVAL / MILESTONE / REVISION
发送会话与当前主管：
本轮状态、关键发现及待决定事项：
完整报告绝对路径与版本：
```

事件 ID 可采用“工作流/任务/派发版本/本轮序号/类型”；取得真实 turnId 或消息回执后可一并登记。它用于去重，不提供认证。收到通知仍要核对发送会话、派发版本及真实产物。约 300 字是预览建议，不是产品上限；不要继承 Claude 快照里的固定截断长度。

区分：调用接受消息、目标实际收到、主管验收通过。首次发送前不预称成功。发送不确定时先核查接收方记录，再决定重试；保留未投递报告，不循环确认。主要产物在通知前稳定；若随后修正，增加报告或派发版本，不能悄悄换掉主管正在验收的结果。

同一结果可能通过主动消息、等待工具和宿主通知同时出现。主管以“来源会话＋任务＋派发版本＋事件ID”识别重复；没有统一事件 ID 时用真实回合和报告版本对账，不能仅凭摘要相似去重。

## 4. 续接与并行汇合

任务状态与宿主运行状态分别保存。active／idle／notLoaded 是运行情况，不是任务成败。以下三项必须分开：

1. 回合结束：可能完成、失败、中断，或在请求用户输入。
2. 报告就绪：本次任务的产物已写完并有完整回报，等待独立验收。
3. 验收通过：主管已检查证据，满足对应依赖；科学主张另行判断。

收到事件时：

1. 匹配工作流、来源、任务及当前版本；旧版／重复事件留简短记录，不覆盖有效状态。
2. 对需要输入或审批的任务及时呈现问题和会话入口；暂停依赖它的步骤，独立任务可继续。审批只能由真实授权与宿主审批路径满足，主管不能借模型消息代批。
3. RESULT 指向实际报告，核对执行轮次和文件版本；必要时等该轮结束，再按风险独立验收。
4. 更新已到、未到、待修订、待验收、已验收集合。决策门所需验收未齐就保持未判定；不能把一个任务完成、暂时 idle 或沉默当作全体完成。
5. 更新计划和当前状态后，按用户已批准的推进方式续接。超范围的新方向仅提出建议。

普通结果可在主管当前工作结束后合并处理；紧急阻塞不必等全部执行者都空闲。发送到忙碌会话的具体投递时机取决于宿主，不把 Claude CLI 或 Desktop 的行为直接移植成 Codex 保证。

有已实测的主动回报能力时，主管可结束本轮等待事件开启下一轮；短检查使用 wait_threads，通常不超过 60 秒，复用每个目标自己的最新 cursor。工具超时不是任务失败。旧 cursor 可能再次返回旧完成；续发 REVISION 时先登记新版本，并将通知与相应新回合对齐。

不要同时开启多套不去重的回报机制。不循环“收到—确认”，不高频轮询，不默认创建定时监控。原生自动唤醒不可用时，明确给用户手动继续入口；需要常驻适配器另按实际缺口与授权设计。

## 5. 用户介入和恢复

执行者收到用户直接变更时，记录变更、版本、已有成果及依赖影响，并在原授权范围内回报主管。用户直接发来的修改优先，不能为了旧任务卡忽略它；涉及共享定义时主管核对后更新计划。

恢复或主管接替时，先读项目计划与执行状态，再读取已登记会话和实际报告。对账有效版本、尚未收到的结果、已接受的结果、暂停／移交项及当前授权；不从一个旧完成消息重启全部任务。notLoaded 会话可仍有完整历史和产物，不直接当作丢失。

更新 current_supervisor 后通知受影响执行者；保留历史来源和旧回执，旧主管不得并行派发同一工作。应用退出、重启和跨机器恢复必须单独实测；项目文件可恢复任务上下文，不等于已证明宿主消息不丢。

## 6. 旁问与模式

旁问默认只解释，不改变有效裁决；需回填时依用户授权发回主管核对。Skill 不能自行切换系统 Plan 模式。已获批计划按实际授权继续，新计划是否等待确认依用户约定，不能机械重复审批。
