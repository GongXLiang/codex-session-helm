# 会话关系、侧栏与生命周期

管理分组、fork、任务交接、解除关联、停止和归档时读取。消息、回报与汇合见[桌面会话协议](桌面会话协议.md)。

## 1. 三种关系分别保存

- 派发关系：工作流 ID、任务 ID、派发版本、原始派发者、当前主管和执行会话。
- 历史来源：新建或 fork；fork 来源及实际继承范围。它不决定今后由谁管理。
- 显示位置：侧栏 sectionId、标题、顺序。移动或折叠不改变任务依赖与回报对象。

真实地址是 threadId 和 hostId；标题、短名和任务编号必须先解析为唯一地址。有歧义时不发送。不得将 App Server 的分析来源字段伪装成任意父子关系。

将这些字段放进已有执行状态文件，仅保留适用字段，不新增竞争的事实来源。多个主管时每张任务仍有一个当前责任人。多层时另外登记父任务 ID、子主管范围和根工作流 ID，任务图必须无环；与父任务有关的依赖由相应主管验收，不能仅靠亲缘关系判定。

## 2. 侧栏组织

在用户批准组织本工作流后，先 list_threads 读取当前 sections、成员和置顶顺序。仅操作本工作流的会话；同名 section 不保证同一工作流，优先复用已登记 ID。

推荐将主管留在组外或按授权置顶，将执行者放入“工作流标识｜执行会话”。这样折叠执行组时主管仍可见。也可依用户偏好全部放入同组，但折叠会隐藏主管。示例标题“执行 T03｜图件修订”是约定，不是平台限制。

当前原生操作按现场 schema 使用：

- create_sidebar_section、rename_sidebar_section：创建、改名；记录返回的真实 sectionId。
- move_thread_to_sidebar_section：迁移与置顶；beforeThreadId 可用于插入，不扰动其他会话。
- reorder_section：必须先读取全体成员并每项恰好提交一次。避免用部分列表覆盖全组顺序。
- delete_sidebar_section：仅移除显示分组，不等于删除会话。依用户授权或已批准的测试清理范围操作。

每次修改后读回目标所在分组。若 sectionId:null 返回成功但仍显示在旧组，可在当前 schema 明确支持时改用 sectionId:"chats" 移出，并再次核实；不要仅凭成功回执判定显示操作完成。

若没有折叠 API，交给用户或可用的 GUI 工具；不能宣称移动分组已验证折叠。需要审批或回答的执行任务应在主管通知中保留会话入口，不能依赖折叠组自动显露。用户手动移动的会话不自动搬回；先确认是显示调整还是解除管理关系。

## 3. 新建、提案与 fork

独立任务默认新建并带自洽的目标、范围、完成标准、Context 和当前有效文件入口。模型主动发现的额外工作先作为提案，用户可选择新会话、当前会话或调整选项；多个已批准、依赖满足的任务才能一起启动。过期或被替代的提案标记撤回，不因曾提出过就执行。

fork 用于需要历史的任务，不用于代替文件隔离。原生工具可能保留中断中的回合；新会话先读取最新计划和裁决，历史里的旧授权或旧假设不自动升级。模型与思考程度未指定时沿用工具默认，不自行挑选低价或更强模型。独立会话的权限须看实际宿主；“只读”提示不是只读沙箱。

本地、SSH、云端分别发现环境和能力。create_thread 的 project 来自 list_projects；云端来自 list_cloud_environments。worktree、分支与起点使用用户已明确指定或批准的值，不能虚构。只读任务可共享目录；可能重叠的写任务经授权使用 worktree 或串行。研究输出用明确的各任务目录也可实现隔离。

## 4. 交接与主管更换

交接是责任转移。写出目标、已完成与待完成步骤、有效裁决、未决问题、任务成员、报告入口、写入范围、未提交改动与用户授权依据。根据需要新建或 fork，取得接收方已读取交接的证据后更新 current_supervisor 和交接版本，并通知受影响的执行会话。原主管不再同时派发同一任务；保留原始派发者供追溯。

新对话历史不代表文件跟着迁移。需要搬文件时核对未提交改动、路径和可写范围，按已有授权处理；不为交接自动提交或推送。

**工具同名陷阱：** 当前 codex-app 的 handoff_thread 是在 checkout 与 worktree 间移动会话及 Git 状态，可能中断运行。它不等于 Claude 的 hand_off_to_session，不用于普通主管换人或转移聊天责任。

用户发来小修正或状态问题时，保持原任务并吸收修正；独立新任务按用户意图新建或交接，不机械地搬走原工作。用户直接修改执行者任务时，执行者记录影响并回报主管；超出本轮定义的部分等待裁决。

## 5. 停止、解除关联、归档

| 操作 | 工作流含义 | 执行约束 |
| --- | --- | --- |
| 折叠／移组 | 只变显示 | 不改任务状态或通知 |
| 停止当前轮次 | 保留已有成果，暂停该次执行 | 优先真实停止接口或 GUI；普通消息未必能立刻中断，未观察到停止就不称已停止 |
| 恢复 | 在原会话继续明确任务 | 核对文件和派发版本，必要时增加版本 |
| 解除关联 | 不再由本主管自动调度 | 保留历史来源，移出显示组，更新等待集合和通知路由；未验收任务记为移交／暂停，不能记完成 |
| 归档 | 收起不再推进的会话 | 核对成员、未完成工作与工作目录影响；按批准的精确范围执行并读回 |

没有原生 detach 时只能实现工作流层解除关联；已存在的宿主回调未必能取消，收到后识别为已解除并忽略自动推进。不能以移组冒充原生 detach。

归档前确认宿主是否连带处理后代；分组关系不保证与宿主后代关系相同。逐个核对真实归档结果，部分成功分别记录。不要用永久删除替代归档，也不以归档授权删除工作目录或未保存的成果。完成后仅清理已获授权的测试分组和测试会话。

读回归档状态时使用实际活动／归档列表及目标历史。section 成员记录可能仍保留已归档 ID，不能据此认定会话仍在活动列表中；恢复后显示 notLoaded 也不等于历史丢失。

## 6. 防止无意扩张

默认主管直接管理一层执行会话。多层任务需有明确子主管范围、最大深度、并发上限或用户认可的资源约束。普通结束通知只触发核对与已授权续接；不能自动开展新方向。没有新事实的确认消息不启动新工作，也不对其继续回信。
